🛡 Operating principle

No standing access, ever

Phase 04 builds one app registration — used by both Terraform (for the 9 groups) and the deploy script (for the 222 policies). One credential, one thing to delete at the end of an engagement, scoped to exactly three Graph application permissions.

✓ Deleted after every real engagement, not just this demo. Once a customer deployment is validated, the app registration — and its client secret — is removed. This is the standing pattern for every tenant this baseline goes into, not a demo-only step.
✓ The baseline outlives the credential. The groups and 222 policies are independent Intune/Entra objects — deleting the app registration doesn't touch them. The customer keeps a fully deployed baseline; what's removed is the standing ability to reconfigure it from outside their own admin workflow.
✓ Why it matters here specifically. DeviceManagementConfiguration.ReadWrite.All is a tenant-wide application permission — not scoped to just the 222 policies this deployment touches. A live credential with that reach, sitting unused between engagements, is exactly the kind of orphaned automation access a security review flags.
✓ Not a one-way door. Returning to a tenant later means re-running the bootstrap script for a fresh app registration — Terraform's state picks up the same 6 groups by their existing IDs, and the deploy script's idempotent get-by-name logic recognizes the 222 policies already there.

See phase 10 for the exact deletion steps.

00

Why two tools, not one

The Conditional Access baseline is one terraform apply, start to finish. This project isn't — and that's worth understanding before you run anything, because it's the one place this deployment genuinely differs in shape, not just in content.

There is no official Terraform provider for Intune device management. HashiCorp and Microsoft haven't shipped one — configurationPolicies, deviceConfigurations, intents, and compliancePolicies simply aren't resources hashicorp/azuread or hashicorp/azurerm know how to manage (the gap is tracked, unresolved, in hashicorp/terraform-provider-azuread #524). The only providers that cover it — deploymenttheory/terraform-provider-microsoft365, terraprovider/terraform-provider-microsoft365wp — are small, community-maintained projects wrapping the same beta Graph API this deploy script calls directly.

What a community provider would cost us
What we chose instead, and why
A third-party trust dependency — its code runs with app-only credentials against every customer tenant
The official Microsoft.Graph.Authentication SDK, calling the same stable REST contract Microsoft documents at learn.microsoft.com/graph — no maintainer we haven't vetted sits between this deploy and a customer's tenant.
An awkward audit answer — "our tooling depends on a solo-maintained GitHub project" is a hard sentence in a NIST/ISO-mapped engagement
"Official Microsoft Graph SDK and HashiCorp's own azuread provider" is a clean one — consistent with how this MSSP already answers that question for the Conditional Access baseline.
Exposure to a maintainer's release cadence — Microsoft's beta Graph endpoints change often; a small provider can lag a fix for weeks
This project regenerates its own request bodies straight from the customer's source JSON via build_baseline.py — no intermediate schema to wait on someone else to update.
Precedent — the CA baseline already answered a similar question once
CA pushed its one Terraform-unsupported object (a Terms of Use agreement) out to a scripted manual step rather than reach for a workaround provider. This project applies the same rule at a larger scale: 222 policies, not one object.
⚠ The honest cost of this choice

Terraform's real value for the 222 policies — a terraform plan diff before anything touches a tenant, state-tracked drift detection, mature idempotency — isn't available here. Deploy-IntuneBaseline.ps1 approximates it by hand: get-all-by-name, then create-or-update, with Verify-Deployment.ps1 standing in for drift detection afterward. That's more code to own, and it's had zero live-tenant runs before today — see the unverified-assumptions tracker in phase 07 for exactly where to expect friction on this first deploy.

So the split is deliberate: Terraform owns the "who" — the 9 device assignment groups, a plain Entra ID object type both providers handle identically — and the Graph SDK owns the "what" — the 222 policy objects themselves, generated fresh from the customer's source pack every time, never hand-edited.

05

Set this customer's values

Four policies in the source pack ship with a placeholder value that actively breaks something if deployed as-is — this is the single most important step in this guide to get right before phase 07.

⚠ The four landmines — see RECONCILIATION.md §8 for full detail
  • OneDrive tenant restriction — blocks OneDrive for every tenant except one hardcoded in the source file, unless replaced with this customer's own Entra tenant ID.
  • Teams tenant restriction — same failure mode, for Teams sign-in.
  • Edge extension management (CIS L2) — ships with an effectively empty allow list; can silently block every extension the customer's users currently rely on.
  • Chrome extension allow list — same failure mode as Edge, for Chrome.

In VS Code's Explorer, right-click config\customer.config.psd1.example → Copy, then right-click config\ → Paste, and rename the copy to exactly customer.config.psd1 (no .example).

⚠ Decide macOS scope now — not mid-deploy

  • Include macOS now — go get the file (security.microsoft.com → Settings → Endpoints → Device management → Onboarding → macOS → Intune), save it somewhere in this project folder, and set MacOSOnboardingXmlPath to that real path before moving on.

Deploy the policies (Graph SDK)

One script, 222 policies, five different Graph object shapes — idempotent by name, so re-running it is always safe. This is also this project's first live-tenant run, project-wide, so read the unverified-assumptions tracker below before you start.

Graph SDK

7.1  Connect

Paste the $cert / Connect-MgGraph block you saved in step 4.4:

cd ..\deploy
$cert = ConvertTo-SecureString '<secret>' -AsPlainText -Force
Connect-MgGraph -TenantId '<tenant>' -ClientSecretCredential (New-Object System.Management.Automation.PSCredential('<app-id>', $cert))
Graph SDK

7.2  Dry-run the whole pack offline first

Before touching the tenant, replay all 212 policies through the deploy script against a mocked Graph API. No tenant, no credentials, no side effects — about a minute:

pwsh ..\test\Invoke-OfflineReplay.ps1

It asserts on every request the script would send: all three rollout stages in both create and update mode, every assignment carrying its tier group and the break-glass exclusion, customer-specific values actually reaching the wire, no leftover placeholders, no over-length descriptions, and the documented Graph endpoints and body parameter names being the ones actually used. Expect All offline replay assertions passed.

⚠ Why this step exists — and why an idempotent script needs it twice

This pack's first live engagement hit seven separate deploy failures, each discovered one run at a time, hours apart. Every one was findable offline. They shared one shape: a code path that had never executed, failing the first time it did. An idempotent create-or-update script has two paths per object shape, and the update path doesn't run until the second deploy against a tenant — so a first clean run only ever proves half the code. The replay runs both. Run it after any change to the deploy script, the source pack, or the generated Intune-Baseline/ output. See RECONCILIATION.md §18 and §22.

Graph SDK

7.3  Pick a rollout stage — defaults to the safest one

-RolloutStage controls how broadly each policy applies, independent of which policies you deploy. It defaults to Pilot, so a first run never reaches a broad group by accident:

StageAssigns toMembership
Pilot (default)Intune-Pilot-<Platform>Manual — a small, deliberately-chosen device set, one ring per platform
StaticIntune-Target-<Platform>Manual — expand over an agreed soak period
DynamicIntune-Target-<Platform>-DynamicAuto-populated by OS type — production. Only exists after phase 09.

Every stage resolves the policy's platform the same way and applies a tier affix, so a platform moves Pilot → Static → Dynamic on its own timeline. Intune-Excl-BreakGlass is added as an exclusion on every assignment, at every stage — break-glass devices are protected regardless of where a policy currently sits. It is deliberately one group rather than four: break-glass is used mid-incident, and a single group has the property that matters under pressure — a device in it is excluded, full stop.

⚠
Endpoint Security intents (Account Protection, BitLocker) — createInstance then updateSettings
Only 2 of 222 policies use this shape. Both paths are now confirmed working against a live tenant (2026-09-08), but they were the source of two separate bugs first: creation had to move to POST /deviceManagement/templates/{templateId}/createInstance (a plain POST /intents is not a create path), and the two actions take the same data under different parameter names — settingsDelta for createInstance, settings for updateSettings. Both are now asserted by the offline replay in step 7.2.
⚠
Edge extension-settings JSON patch — category 11, CIS L2
The ExtensionSettings JSON map the script builds from EdgeApprovedExtensionIds is inferred from Microsoft's general Edge policy documentation, not observed directly in the source file (its recorded value is a bare wildcard). Confirm the patched value actually renders correctly in the Intune portal or on a test device before trusting it for a real customer.
⚠
ASR audit-mode substitution — the 3 audit_first_recommended policies
A targeted regex swap on the ASR action enum (block→audit), flagged in the script's own comments as an unverified assumption about how that enum is encoded. Confirm each of the 3 flagged policies actually shows as "Audit," not "Block" or "Not configured," in the portal after this run.
⚠
Break-glass exclusion — a mixed include+exclude assignments body, every policy
Every /assign call now sends the tier's inclusion group alongside Intune-Excl-BreakGlass as an exclusionGroupAssignmentTarget in the same request. This is Microsoft's documented pattern, but it hasn't been exercised end-to-end against a live tenant for all 5 object shapes here. Spot-check a couple of policies in the portal to confirm the exclusion actually shows up.
⚠ If a policy fails partway through

The script is idempotent by name — re-running .\Deploy-IntuneBaseline.ps1 with the same arguments skips everything already created and retries only what's missing or failed. Note which category and policy name it stopped at before re-running.

09

Promote a platform to production

Not all policies suit every business, and security doesn't get to automatically trump productivity — this is the deliberate, risk-based step where a platform earns its way from a hand-picked pilot into full auto-enforcement. Do this per platform, only once you're actually happy, never as a default.

Terraform will perform the following actions: + azuread_group.target_windows_workstations_dynamic[0] Plan: 1 to add, 0 to change, 0 to destroy.
⚠ Why this is a new group, deliberately

The azuread_group resource's types argument (what turns dynamic membership on) is ForceNew in the hashicorp/azuread provider — flipping it on the existing static group would make Terraform destroy and recreate it, silently orphaning every policy assignment that pointed at its old object ID. A second group with a new ID sidesteps that entirely; the static group stays behind as a harmless record of who was in the pilot/expansion set.

Leaving it clean

Intune / Entra Portal

10.1  Delete the app registration

This is the step that makes the no standing access principle at the top of this page real. Do this once you've validated the deployment — don't leave it for "later." Because both tools share this one app registration, deleting it revokes both Terraform's and the deploy script's access at once.

Entra admin center → App registrations → All applications, find Intune-Baseline-Deploy, open it, and Delete.

⚠ Verify the deletion — don't just trust the click
Connect-MgGraph -Scopes "Application.Read.All" -NoWelcome
Get-MgApplication -Filter "displayName eq 'Intune-Baseline-Deploy'"

No output back means it's gone.

✓ What stays behind, on purpose

The groups and 222 policies keep existing and keep enforcing — independent objects, not owned by the app registration. Deleting the app removes the credential that could reconfigure them, not the controls themselves.

Terraform

10.2  Clean up local secrets and state

The customer's ARM_* secret is already dead once 10.1 is confirmed — but delete app-registration.env, config\customer.config.psd1 (the real one, not the .example), terraform\terraform.tfvars, and terraform\.terraform\/*.tfstate* from this customer's folder once your engagement file has whatever record it needs — including which platforms, if any, were promoted to the Dynamic tier and when, since that history lives only in terraform.tfvars and the archived state. A dead secret sitting in a folder is still a dead secret sitting in a folder.

This project has not yet been run against a live tenant — something not matching this guide exactly on this first run is expected, not a sign you did something wrong. Here's what's actually useful to send over, by situation:

01

A red Terraform error (init, plan, or apply on groups.tf) — copy the entire red block, top to bottom.

02

The deploy script errors partway through — which category and policy display name it had reached, and whether you passed -Categories/-SkipCategories or the default -AuditModeForFlaggedPolicies.

03

Test-CustomerConfig throws a validation error — the exact error text; it names the specific production note and field, so that's usually enough to fix on its own, but send it anyway so the pattern is on record.

04

A portal screen looks different from what's shown here — a real screenshot beats a description; Microsoft moves menu items around more often than the underlying API changes.

05

One of the 4 unverified-assumption areas from phase 07 looks off — which of the four, and exactly what you see in the portal versus what was expected.
